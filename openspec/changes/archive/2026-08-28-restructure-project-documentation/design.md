## Context

参见 `proposal.md` 的改造动机。首轮重构已经生成根 README、技术架构、统一评测报告和评测证据目录，但核心文档仍有三个结构问题：技术架构同时承担外部调研、内部设计和远期方案；端到端链路按阶段逐项展开，却没有优先解释 DSL、组件和算法为何存在；评测方法论位于结果之前且与文末验证优先级重复。

本轮只修订文档，不改变实现、协议、测试数据或历史审计结果。当前事实仍以源码、共享合同、OpenSpec 主规格和 ADR 为准；外部方案事实以带日期的调研文档为准。

## Goals / Non-Goals

**Goals:**

- 为 README、技术架构、评测报告和方案调研建立不重叠的职责边界。
- 让技术架构先讲清关键组件、DSL、算法及其必要性，再通过实例说明数据流动和协作关系。
- 保留对正确性、安全性和状态保持有决定作用的设计理由，删减机械步骤和次要实现细节。
- 将后续方向限制为由当前问题、业务需求和测试证据触发的渐进式升级。
- 将评测数据覆盖与后续设计合并到报告末尾，并执行可读性和去重检查。

**Non-Goals:**

- 不修改运行时行为、合同、API、代码、测试 runner 或审计数据。
- 不新增文档；复用既有 `docs/research/generative-ui-layout-comparison.md`。
- 不为旧组件兼容、布局质量评分、自动降级或新数据集预先设计完整 Schema、算法和实施任务。
- 不把核心技术解释压缩为只有结论的摘要；稳定 ID、分层校验和原子提交等关键理由仍须保留。

## Decisions

### 1. 将外部灵感与完整方案比较迁移到既有调研文档

`docs/research/generative-ui-layout-comparison.md` 作为外部灵感和方案比较的唯一完整信息源，承载：

- Google A2UI、json-render、MCP Apps 等项目与协议的相关机制；
- 本项目从外部方案中借鉴和主动收窄的设计；
- 在本项目方案边界说明完整之后，从协议、身份、渲染、安全和旧资产复用等必要维度进行比较；
- 资料日期、来源和“当前事实/历史决策输入”的边界。

`docs/technical-architecture.md` 只用短节概括 Catalog、声明式 IR、native Renderer、稳定身份和原子更新等设计来源，并链接调研文档，不再复述外部项目流程或完整比较。根 `README.md` 的文档地图为该调研文档提供明确入口。

继续把比较放在技术架构中会打断内部设计主线；另建新文件则会与现有调研文档重复。因此选择复用现有调研文档。

### 2. 技术架构采用“概念—理由—关系—实例”结构

技术架构按以下顺序重组：

1. 业务目标、边界和整体架构概览。
2. 关键组件及职责。
3. DSL 与受控合同。
4. 重要算法及存在理由。
5. 一个具体请求中的数据流动与组件协作。
6. 辅助业务流、模块索引、安全边界和当前局限。
7. 精简的后续展望。

关键组件只选择影响架构理解的参与者：Qt Host、业务 QWidget 与 WidgetRegistry、后端 Agent Service、LLM Adapter、LayoutPlan Parser/Validator、Surface Compiler、SurfaceSpec Validator、Reconciler/Renderer。每项说明它负责什么、不负责什么，以及缺少该边界会产生的风险；不把文件清单当成组件说明。

DSL 与受控合同必须明确区分：

- Catalog 描述系统允许注册的组件能力，Effective Catalog 是当前运行时真正可供生成使用的权威白名单，而不是模型可扩写的建议。
- LayoutPlan 是 LLM Adapter 生成的受限意图计划，表达 `existing`、`new` 和 Row/Column 组合，但不承担最终稳定身份与渲染合同。
- SurfaceSpec 是 Compiler 生成的完整渲染目标，以稳定 ID 和平铺引用图描述可提交的 Surface。
- 两层 DSL 将概率性的意图表达与确定性的渲染合同分开，使模型不能直接决定 QWidget 身份或绕过编译和校验。

重要算法聚焦四个难点，并优先解释为什么：

1. **分层格式与能力校验**：不同阶段分别拦截 JSON/字段问题、Catalog 越界、计划语义错误、引用图错误和客户端信任边界问题。说明各层保护的边界及不可简单合并的原因，不逐项抄写全部字段规则。
2. **稳定 ID 编译**：ID 是跨次编排识别同一业务组件、复用 QWidget、保持焦点和局部状态的身份键。Compiler 单独分配 ID，让确定性代码而非 LLM 掌握身份，并使规则可重放、可审计。
3. **SurfaceSpec 图校验**：把平铺节点解释为有向引用图，验证唯一性、引用、无环、单父和可达性，确保 Renderer 接收到明确且有限的布局树。
4. **事务式 Reconciliation**：以 `(id, type)` 判断复用、新建、替换和移除，先暂存、后提交；任何失败保留最后有效页面，避免半更新破坏对象状态。

不再用八个同等篇幅的小节描述完整执行顺序。网络交付、错误码和布局属性只在它们影响信任边界、数据不变量或最终行为时展开。

### 3. 用一个可复核实例串联组件协作

在概念和算法解释之后，使用“计算器在左、历史记录在右，宽度 2:1”的请求作为主实例，只展示理解协作所需的信息：

- 当前 Surface 与 Effective Catalog 如何限制 LLM Adapter；
- LayoutPlan 如何区分复用组件和新组件；
- Validator 与 Compiler 如何把计划变成带稳定 ID 的 SurfaceSpec；
- Qt 如何依据 `(id, type)` 复用 QWidget，并把 `weight` 映射为布局 stretch；
- 暂存成功后如何一次提交，失败时为何不改变活动页面。

实例的目标是解释数据为何变化、下一组件依赖什么不变量，以及设计如何满足安全、可审计和状态保持需求。代码、完整 JSON 和每个 HTTP 字段仅在不可替代时出现。

### 4. 后续方案只保留渐进式展望

技术架构和 README 不再给出四级兼容框架、完整认证矩阵或“测量—分配—评分—降级”算法。后续方向统一采用“当前问题—最小下一步—升级触发条件”的表达：

- 先根据现有长尾和语义 no-op 证据改善超时口径、诊断和意图判断；只有持续测试证明必要时再扩展生成或校验能力。
- 先用少量代表性旧 QWidget 验证直接注册和薄 Adapter；只有真实组件暴露生命周期、ABI 或隔离问题时再设计更复杂的接入层。
- 先利用现有 Qt size hint、`QSizePolicy`、stretch 和滚动行为改善明确的排版问题；只有可复现视觉缺陷无法解决时再引入元数据或质量判定。

这些内容只描述方向和触发条件，不承诺尚未实现的架构，也不为假设性需求创建 task。

### 5. 评测报告以当前证据为主，数据集演进放在文末

`docs/verification-and-evaluation.md` 保持“结论与口径—当前测试结果—Provider 结果—已确认问题—失败保护”的主线。现有“评测数据集如何设计”从报告前部移除，与“后续验证优先级”合并为文末“后续优化方向”，固定使用以下顺序：

1. 当前数据集实际覆盖了什么，包括七场景、50 样本、固定 seed SurfaceSpec 和合同 Fixture 的不同职责。
2. 当前证据尚不能支持什么结论，只保留影响结果解释或下一步决策的主要缺口。
3. 后续如何按已发现风险补充意图断言、边界/反例、状态迁移、缺陷回归或重复采样；先扩充最小回归集，再由新业务和失败数据决定是否引入更系统的追踪或门禁。

等价类、边界值、判定规则等测试术语只在解释当前覆盖和预期结果时使用，不单设长篇方法论。后续方案不重复问题章节已有的处置建议，也不把样本总数包装成覆盖率或产品通过率。

### 6. 最后执行跨文档编辑复核

实施完成后逐段检查四份目标文档：README 只保留价值、快速入口、当前结论和索引；技术架构只完整解释本项目内部组件、合同、算法和协作；调研文档只完整解释灵感来源与方案比较；评测报告只完整维护验证事实、问题边界和后续证据方向。

删除可由链接替代的重复段落，拆分过长句子，避免连续罗列实现步骤；首次出现的 DSL 和组件名必须有简短定义。最后检查相对链接、标题层级、术语一致性，以及“当前实现”“历史证据”“后续展望”的表述边界。

### 7. DSL 示例和 Qt 几何说明跟随对应模块

技术架构在 Catalog、LayoutPlan、SurfaceSpec 各自的子标题下增加一个与当前合同一致的最小示例，
并链接权威 JSON、Schema、Fixture 或语义文件。示例只帮助读者识别数据形态，不复制完整 Schema，
也不引入当前实现不存在的字段。

`QWidget 几何映射` 作为布局语义的唯一完整讲解位置，按 Row/Column 容器方向、嵌套相对位置、
`children` 顺序、`gap`、`align`、`justify`、`weight` 与 Qt 尺寸约束的顺序解释。使用一个最小嵌套
结构展示多个 Row/Column 如何递归组成布局；实例章节只说明该请求的数据变化，不重复字段手册。

补充前以 `shared/catalog/`、`shared/schema/`、`shared/protocol/layout-semantics.md`、合同 Fixture 和当前
Renderer 为事实依据。若发现未在文档提及的重要 DSL 字段，只补充当前业务理解所必需的字段和边界，
遵循 MVP 原则，不扩展协议或预先设计新能力。

## Risks / Trade-offs

- [拆分后读者需要跳转文档] → README 和技术架构提供清晰索引，技术架构保留理解内部设计所需的最小来源摘要。
- [过度压缩会丢失关键正确性理由] → 保留两层 DSL、分层校验、稳定 ID、图校验和原子提交的必要性，并用实例检验解释是否完整。
- [调研文档与技术架构再次重复] → 外部机制与跨方案比较只在调研文档完整展开；内部算法与当前实现只在技术架构完整展开。
- [后续方向过于抽象而无法行动] → 每个方向保留当前证据、最小下一步和升级触发条件，但不提前设计未被需求证明的复杂方案。
- [字段说明演变为 Schema 复刻并再次拉长主线] → 正文只解释读者理解布局所需的语义、取值差异和最小示例，完整约束继续链接权威文件。

## Migration Plan

1. 更新既有调研文档与 README 索引，确定外部灵感和完整比较的新边界。
2. 按“概念—理由—关系—实例”重构技术架构，并压缩后续展望。
3. 将评测数据覆盖、缺口与后续设计合并到评测报告末尾。
4. 对四份目标文档执行去重、可读性、当前/未来边界和 Markdown 链接检查。

实施前应先保留可审查的 diff 或提交点；若修订造成信息缺失，可据此恢复对应段落。该回滚不涉及运行时或审计数据。
